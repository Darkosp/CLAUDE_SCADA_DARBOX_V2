# The walk to take now — 2026-10-06

**Twenty minutes, and it is the only thing in this project that no test can do.** Phase 5.5's walk
found ten defects the suite had passed. Phase 8's found four. Both were found by a person looking at a
screen, and both were things a machine cannot see.

Everything below is built, tested and deployed. What is missing is judgement.

## Before you start

The stack is up at **http://localhost:8090**. Sign in as `admin` / `walk-admin-secret`.

Hard-refresh once (`Ctrl` + `Shift` + `R`). Phase 6.5 learned that the hard way: a browser holding the
previous client while the server is new shows you a defect that is not there.

Two things to know about the screen you will be looking at:

- it is a **demo screen** built for this walk, not a seeded one. The `tools/seed-demo-screen.mjs`
  script writes it and can rebuild it at any time;
- the reading changes every few seconds, because a simulator is feeding it.

## 1. The pump — the newest thing, and the one nobody has seen move

**Go to `Screens`.** The second row holds a circle with four vanes and two pipes.

**Look at:**

| Question | Why it is asked |
|---|---|
| Is it **turning**? | The animation runs on a 1.6-second loop. A screenshot cannot show it, so this is the only way it gets checked at all. |
| Can you tell it is running from the **drawing alone**, without reading `RUNNING` under it? | If not, the drawing is decoration and the word is doing all the work. |
| Does it read as **a pump**, or as a fan, a valve, a compass? | The shape is four vanes and a hub. It is the part most likely to need redrawing. |

**Then make it stop.** Open `Browse`, pick `Pump Running`, and write `false` to it if the tag is
writable; if it is not, watch until the simulator turns it off — it does so on its own cycle.

**Look at:** the pump should go **grey and still**, and say `STOPPED`. Green should be gone entirely.

**The question that matters most here:** is `STOPPED` **obviously different** from `BAD`? A stopped pump
means the plant says it is off. A `BAD` pump means nothing is measuring it. Those are different facts
and an operator acting on the wrong one is the failure ADR-0003 exists to prevent. The drawings differ
by colour and by a cross, and there is a word under each — **but is that enough at a glance?**

You can force a `Bad` reading by stopping the device: `docker stop scada-darbox-modbus-sim-1`. The tag
should go Bad within a few seconds, and the pump should draw crossed out. Start it again with
`docker start scada-darbox-modbus-sim-1`.

## 2. The dark theme

**Press `Dark`** in the header, to the right of your username.

**Look at:**

| Question | Why |
|---|---|
| Is the **status green** still readable? Used on the quality pills and on the running pump. |
| Is anything **hard to read**? Especially the small grey captions and the timestamps. The contrast was audited and every pair passes AA — but "passes 4.5:1" and "comfortable to read" are not the same sentence. |
| Does the **layering** hold up? Cards should look like they sit *on* the page, not behind it. |
| Does anything look like an **accident** — a white box, an invisible border, a chart line you cannot see? |

Then press `Light` and check the same screen has not lost anything.

## 3. The screens view at 1920 — the size a panel is

The screenshots for this were taken at 1920×1080 because that is what a control-room panel is. **If you
are reading this on a smaller laptop screen, press `Ctrl` + `-` once or twice** to see what an operator
sees.

**Look at:**

| Question | Why |
|---|---|
| Can you read the **values from a step back**? | The reading scales with the viewport now. Whether the scale is right is a judgement. |
| Are the **quality pills** noticeable? | Green `GOOD`, amber `STALE`, red `BAD`. If you cannot tell them apart without reading them, they are not doing their job. |
| Does the **zero** stand out? | `Suction Flow` reads `0.00` and is deliberately dimmed. Is that the right treatment, or does it look broken? |
| Are **twelve columns** enough? | The demo uses 3+3+3+3 and 3+5+4. A real screen will want more. |

## 4. Building a symbol yourself — the newest path, and the least used

This is the part that was verified by script and **not by a person**.

1. `Screens` → **Edit**
2. Under **Add a component**: `Kind` → **Symbol**
3. `Tag` → pick anything
4. **Add to row 1**

The new cell should appear with a form under it: a `Symbol` picker reading `pump`, and two rules —
`running` / `is` / `true`, and `stopped` / `anything else` / (disabled).

**Look at:**

| Question | Why |
|---|---|
| Is the form **understandable** without having read ADR-0027? | If you have to ask what `anything else` means, an operator will too. |
| Does the **preview below** show the new symbol, live? | It should, drawn by the same component the operator's view uses. |
| Try `Add a state`. Does the new row make sense? | It arrives as `running` / `is` / (empty), which is a rule that matches nothing until you fill it in. |
| Try setting a row to **`anything else`** and back. | Choosing it clears the comparison; choosing `is` brings it back empty. Is that predictable? |
| **Save.** Does it save without a refusal? | The API refuses a symbol whose rules name a state the pump cannot be drawn in. Making that happen on purpose would be useful, but is not required. |

**Then press `Cancel`** rather than leaving your test on the demo screen, unless it is useful — this
screen is what the next person will walk.

# Walked by script: ADR-0023's write over a real link � 2026-10-06

**This half was done by a machine, and it is recorded separately because it is a different kind of
evidence.** The five questions above need eyes. This one needed a broker, an edge and a device, and it
had all three.

**What was set up.** The cloud stack (`deploy/cloud`) at commit `25dac80`, its broker over TLS on the
cloud network; the on-premises Modbus simulator joined to that same network; an edge agent
(`plant-b`, certificate signed by the walk's own CA) joined to both networks; and the device
`Pump Station PLC` assigned to that edge and pointed at the simulator.

**What was proved, and how.**

| Step | Evidence |
|---|---|
| The cloud derives the edge's configuration and sends it | The edge logged `Configuration sha256:9d77ff� accepted, derived by the cloud at �: 1 device(s), 1 tag(s) to read` |
| The edge reads the device | `Connected to device Pump Station PLC`, and readings arrive in `tag_sample` every second |
| **A write is routed to the edge over the link** | The API answered **HTTP 204 in 29 ms** and again in **56 ms** � no direct connection was attempted, because the device is only reachable from the edge's network |
| **The edge wrote it to the device** | The edge logged `Wrote tag b418c2d9� on device Pump Station PLC as the cloud asked` |
| The cloud answered only after that | The 204 came back in milliseconds of the reply, not on a timer |

**Two things the walk found, and the first is worth more than the pass.**

1. **Updating a device through the API clears its edge assignment unless `edgeId` is sent again.** The
   first write attempt answered **HTTP 502 after 4.75 s** with `The device did not accept the write:
   Name or service not known`. That was not the link failing: the assignment had been dropped by the
   device update, so the cloud tried to reach `modbus-sim:5502` **directly**, could not resolve a name
   that exists only inside another network, and reported the device's refusal. **The refusal was
   correct and the latency was correct** � it is the honest answer to "the cloud cannot reach this
   device". What was wrong was the assignment, and the API accepted the update that caused it without
   saying that an edge assignment was being dropped. **Full replacement semantics on a device that
   carries an assignment is a defect worth fixing**: an operator editing a hostname should not
   silently detach a device from its edge.

2. **The written value cannot be seen in the readings, and that is the simulator rather than the
   write.** The simulator overwrites its register on every scan, so the value written is replaced
   within a second. The proof that the device took it is the edge's own log line and the sub-100 ms
   204, not a value observed afterwards � and saying so is more honest than presenting a reading that
   happens to look right.

**What this does NOT prove**, and it is the same gap Phase 7's own record carries: no real arm64 board
and no second host. The broker, the edge and the device were all on one machine, reached over Docker
networks. The link was real in the sense that it was TLS to a real broker with real certificates; it
was not real in the sense of two pieces of hardware and a cable between them.
