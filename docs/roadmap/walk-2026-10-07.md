**The three items `open-work.md` §2.0 had carried as written, implemented, tested and never walked.**

the last of Phase 7's open work that needs neither hardware nor a decision.

All three were walked in one sitting, against one rig, because they meet in one place: **a new edge**.
ADR-0022 is about how its link comes into being, ADR-0020 about what is left out of what it is sent, and
ADR-0021 about what it says back.

## ADR-0022 — an edge's link device is derived, and is not overridable

**The edge was created with a `linkDeviceId` that was deliberately wrong:**

```
POST /api/edges  {"name":"plant-c","linkDeviceId":"11111111-2222-4333-8444-555555555555"}
→ 201
```

| Claim | Evidence |
|---|---|
| The sent id is ignored | the edge reads back `linkDeviceId: ca67d3b8-417b-4287-a5ac-4d15ac318fb1` — **not** what was sent |
| …and the request is still recorded | the `edge.create` audit row holds `"LinkDeviceId": "11111111-…"`, so what was asked for is not lost, only not obeyed |
| The link is derived from the deployment | `Derived edge plant-c's link device Edge plant-c: subscribing to scada/edge/plant-c/samples, silence allowed for 60 s (ADR-0022).` |
| The Gateway subscribes **before the edge starts** | `Subscribed to scada/edge/plant-c/samples on broker:8884 (new session).` — logged while **no edge agent existed at all**; the container was created 50 minutes later |
| An existing deployment's links are reused, not replaced | `plant-7` and `plant-b` kept link ids `57bb1302…` and `63fa283e…` across the upgrade from `25dac80` to `4fa715f`; the broker audit shows the same client ids connecting on 2026-10-05, 10-06 and today |

**One thing the walk sharpened.** The subscription is not made when the edge row is created — it is made
when the edge first has something to read. `plant-c` was created with 0 devices and the Gateway logged
only the derivation; the `Subscribed to …` line came when the first device with a tag was assigned.
That still satisfies what ADR-0022 owes — **before the edge is started** — and it is worth writing down,
because "created an edge and saw no subscription" is otherwise a reasonable thing to mistake for a
defect.

## ADR-0020 — a device with no tags is omitted, and the operator is told

**Both halves walked, and the second half is what the ADR is really for.**

| Step | Evidence |
|---|---|
| A tagless `modbus-tcp` device (`Tagless Booster`) assigned to `plant-c` | accepted, `201` |
| It is **not** in the derived configuration | the configuration went `0 → 1 → 2 → 3` devices as tagged devices were added; the tagless one never appeared in a count |
| Its first tag is added | `POST /api/devices/{id}/tags` → `201` |
| The edge picks the device up **with no second edit** | `A newer configuration arrived; restarting acquisition.` → `Reading 3 device(s) …` → **`Connected to device Tagless Booster.`** |

### And the defect this found

**The report that tells an operator about the omission was never written when it mattered.**

`Tagless Booster` was assigned at **08:38:46** and the Gateway said nothing. The line

> `Edge plant-c has 1 device(s) assigned with no tags, so they are not in its configuration: Tagless
> Booster. The edge reads nothing from them until one of their tags is added (ADR-0020).`

appeared at **08:40:04** — four minutes later, and only because an **unrelated** device gained its first
tag and forced a publish. Had that not happened, it would never have appeared.

The cause, from the code: `ReportOmitted` was the last statement of the publish branch, after the
`continue` that skips an edge whose revision has not changed — **and the revision never changes in this
case**, because a tagless device is omitted whether or not it is there. Fixed, with a test that asserts
the pair *the report is written* **and** *nothing was published*
([PR #2](https://github.com/Darkosp/CLAUDE_SCADA_DARBOX_V2/pull/2)).

**This is the walk earning its place.** Every unit test of the derivation passed and still passes: they
test `DevicesFor`'s `omitted` output, which was always correct. What nothing tested was whether anyone
is ever *told*.

## ADR-0021 — an edge says what it has been assigned and cannot read

`plant-c` had never declared, so under ADR-0019 §8 it could still be assigned a device whose driver no
edge build has — *an edge that has not declared is not an edge that has declared it has nothing*. A
`mqtt` device (`Remote Sensor`) was assigned and given a tag; it was accepted, `201`.

Then the edge was started.

| Claim | Evidence |
|---|---|
| The edge refuses the device and says which | `Device Remote Sensor needs driver 'mqtt', which this edge agent does not have.` |
| …and accepts the rest of the configuration whole | `Configuration sha256:04b8b018… accepted, derived by the cloud at …: 2 device(s), 2 tag(s) to read.` then `Connected to device Pump C.` |
| It reports it on the declaration it already publishes | `This edge cannot read 1 device(s) assigned to it, and has said so on scada/edge/plant-c/drivers: Remote Sensor (needs 'mqtt').` |
| The cloud records it by name and by driver | `Edge plant-c reports it cannot read device Remote Sensor, which needs driver 'mqtt' and is still assigned to it. The assignment is left as it is.` |
| `/api/edges` exposes it | `unreadableDevices: [{deviceId: dce022b9…, device: "Remote Sensor", driver: "mqtt", reportedByEdge: true}]` |
| **The assignment is unchanged** | `deviceIds` still 3; `linkDeviceId` unchanged |
| §4 — republished when the set changes, and not otherwise | two audit rows 200 ms apart: the connect-time declaration with `reportedUnreadableByEdge: []`, then the post-acquisition one with `["Remote Sensor"]` |

### The payload version, on a real link for the first time

This is the project's first payload version bump, and until now the claim that the cloud reads version 1
and refuses version 3 had been tested against this build and never over a link. Both were published by
hand onto `scada/edge/plant-c/drivers` with **plant-c's own certificate**, which also re-tested the ACL.

**Version 1** — `{"version":1,"drivers":["modbus-tcp"]}`:

```
08:42:50.323  edge.drivers_declared  drivers=["modbus-tcp"]  unreadableReported=false  reported=[]
```

`unreadableReported: **false**` — the field is **absent**, and the record keeps that apart from the
version 2 message 75 seconds earlier which had `unreadableReported: true` with an **empty** list. That
is ADR-0021 §2 exactly: *absent is not empty*, and the two states are distinguishable in what was
stored.

**Version 3** — a plausible future message with an extra field, published with the edge stopped so
nothing could restore the state:

```
The declaration from edge plant-c on scada/edge/plant-c/drivers was refused: version 3 is not
understood (this build reads versions 1 to 2). The cloud keeps the last one it read.
```

Refused whole, by name. Afterwards `declaredDriverKeys`, `driversDeclaredAtUtc`, `unreadableDevices` and
`deviceIds` were all unchanged, and **no audit row was written**.

## Two things about the method, so the next person does not lose an hour

**Publishing by hand with an edge's certificate disconnects that edge.** `mosquitto_pub` with
`plant-c.crt` connects **as `plant-c`** — the broker takes the identity from the certificate — and
MQTT's same-client-id rule evicts the running agent, which reconnects immediately and republishes. The
broker audit shows all three connections. It is not a defect, and arguably it is the property you want
from one certificate per edge; it does mean that to test the cloud's handling of a hand-made message you
must **stop the edge first**, or you are watching the edge put its own answer back.

**Git Bash rewrites container paths.** `-e Edge__Broker__CaFile=/app/certs/ca.crt` arrived inside the
container as `C:/Program Files/Git/app/certs/ca.crt`, and the agent refused to start, correctly naming
all three missing files. `MSYS_NO_PATHCONV=1` on the `docker run`. The agent's refusal was the thing
that made this a two-minute problem rather than an hour's.

## What this does **not** prove

The same gap Phase 7's own record carries, and the walk of 2026-10-06 carried before it: **one machine.**
The broker, the Gateway, the edge and the device were all on this host, reached over Docker networks.
The link was real in that it was TLS to a real broker with real certificates and real per-edge
identities; it was not real in the sense of two pieces of hardware with a cable between them. A real
arm64 board remains `open-work.md` §1.3, and it is the one item no amount of software closes.

**And nobody looked at any of it on a screen.** This walk was driven through the API and read out of
logs, the audit trail and the database. Whether the `unreadableDevices` state is *noticeable* on the
Edges panel — whether an operator would see that one of their devices is assigned and unread — is
unjudged, and is the same class of question every Phase 8 item carries.

# The pump, walked by eye — 2026-10-07

**A second walk the same day, and a different kind.** Everything above was driven through the API and
read out of logs; this was a person looking at a screen, on a stack built from `6c7117e` and
hard-refreshed. It is the walk `open-work.md` §2.0j had been waiting for since ADR-0027 shipped: *has
anybody actually looked at a turning pump.*

## What held

| State | What it looks like |
|---|---|
| `RUNNING` | green circle, four vanes, turning; `RUNNING` in green beneath |
| `STOPPED` | grey circle, vanes still, hub a filled dot; `STOPPED` beneath |
| Dark theme | the green stays readable, the layering holds, nothing reads as an unstyled accident |

The tiles above it behaved as designed too: `GOOD` while fresh with no timestamp, and on a Bad reading
a dash, a `BAD` pill and `last at 14:02` — the time appearing **only** when the reading is not fresh,
which is the rule the 1920 work introduced.

**And one thing this confirmed that was not the point of the walk:** a symbol bound to the numeric
`Discharge Pressure` drew `RUNNING` at 5.00. That is the mapping fix from earlier the same day working
in the running application — before it, a numeric tag drew `stopped` for ever.

## The defect: a Bad pump was not a cancelled machine, it was a busier one

The four vanes sit on a **plus**. The two cross lines that mark a Bad reading sit on a **diagonal**.
Together they drew an **eight-pointed star**.

So the crossed-out pump read as a pump with *more* vanes. Put the two states side by side and it is
worse: `STOPPED` is a plus in a circle, `BAD` was a star in a dashed circle — **the dead one looked
more active than the stopped one**, and the only thing left separating *nothing is measuring this* from
*the plant says it is off* was a change of colour.

That is ADR-0003's distinction collapsing in the medium where it is hardest to notice. ADR-0027 §4 had
already said what was wanted, in the component's own comment — *a picture of a machine with no reading
"is not drawn as a machine at all"* — and the drawing did not do it.

**Fixed** ([PR #3](https://github.com/Darkosp/CLAUDE_SCADA_DARBOX_V2/pull/3)): in `bad` the rotor is not
drawn at all. What is left is the dashed body, the pipes and a cross heavier than a vane. Confirmed by
stopping the simulator and looking: it is now an unmistakable cancellation.

**Why this one is worth dwelling on.** Every test passed, before and after. The states were derived
correctly, the quality override worked, the colours were the audited ones. What was wrong was what the
lines added up to — and nothing in this repository can see a sum of lines. It is the clearest case yet
for the rule that a phase with a screen is not done until somebody has used the screen.

## The answers, from the person who looked

These are the questions `walk-2026-10-06.md` ends with. **Three are answered now**, in the words they
were given in, because a paraphrase of a judgement is not the judgement.

- **Does the rotation read at a glance?** — **Yes.** *"ротацијата се фаќа со поглед."* Settled, and it
  is the one thing no screenshot, no test and no headless browser in this repository could have told
  us.

- **Does the drawing read as a pump?** — **Qualified yes, and the qualification is the useful part.**
  *"личи на нешто што симболизира пумпа — тоа се 4 тенки крака во круг кои вртат."* It reads as a
  **symbol of** a pump rather than as a pump: four thin arms in a circle, turning.

  Whether that is a defect is a decision nobody has made. On a P&ID a pump **is** an abstract mark, and
  "something that symbolises a pump" is what such a drawing is for — by that reading this is success.
  But the convention most plant people are trained on is a circle with a **wedge** marking the
  discharge, and four vanes reads closer to an impeller or a fan. **Changing it is cheap** (ADR-0027
  §6: a drawing and a state list, not a decision) and it is not this walk's to decide.

- **Is a dimmed `0.00` a true zero or something broken?** — not contradicted: the reader read it as a
  zero and moved on. Recorded as *not objected to* rather than as *judged*, which is a weaker claim
  and the honest one.

- **Is the mapping form usable by somebody who has not read ADR-0027?** — **unanswered, and the way it
  went unanswered is itself evidence.** The question was put using the phrase *"the mapping form"*, and
  the reply was *"I do not understand what that is."* The questioner's own wording, not the product's,
  but it is the second time this slice has produced a name only its author knows: ADR-0027 calls it a
  *mapping*, the form itself says `Symbol`, `is` / `above` / `below` / `otherwise`, and nothing on the
  screen ever uses the word. **A feature whose name exists only in an ADR is a feature an author cannot
  ask about.**

A second symbol — a tank, a valve — is now *cheap* (ADR-0027 §6: a drawing and a state list, not a
decision), but **none of it is the mimic**: free positioning, pipe routing and nesting remain
undecided, and the grid is still twelve columns of tiles.

# The trend, walked by eye — 2026-10-07, second sitting

**One open judgement from `open-work.md` §2.6, and it was the last thing ADR-0029 owed.** The reduction
moved into the query that day and every test of it was green; what no test could answer was whether the
picture it drew was *readable* — whether the caption says something an operator can use, and how an
envelope at a coarse resolution looks. It found a defect that had been on screen since the chart was
written, and not one this change caused.

## The rig

A Gateway run from this branch against a scratch database on `scada-test-db-5433` (migrated with the
real Migrator, port 19), the client from `src/Web` served by `ng serve` on `:4200` through the dev
proxy, and the instrument that reviewed this client's look the first time:
`tools/screenshot-live.mjs`, extended in this sitting with the step it lacked — select the first tag,
then shoot **every window the picker offers**, because both the caption and the envelope depend on how
much of the window holds readings at all.

**The data is seeded and that is stated rather than implied**: 169,057 readings for the demo's
`Discharge Pressure`, one a second over two days, carrying the three shapes a trend has to survive — a
slow drift, a fast ripple, **a one-hour outage nothing was measured in**, ten minutes in which the
device answered with no value at all, and one four-second excursion to 9.7 bar forty minutes before the
end. Seeded through `psql`, so the buckets are arithmetic rather than timing. Nothing in it came from a
plant.

## The defect: the chart was not drawn where its axis was

**Measured on the running client**: the chart element is **1482×162 px**, its `viewBox` was the constant
`0 0 600 160`, and it set no `preserveAspectRatio` — so SVG's default scaled the drawing uniformly to fit
the *shorter* side and centred it. The first drawn point sat at **x=846 of 1887**.

What that means on screen: the curve was drawn in a **607 px strip in the middle of the card** while the
axis beneath it ran edge to edge, and the two value ticks floated in the middle of the chart instead of at
its left edge. **Every reading was placed at the wrong time by the width of the empty band** — about
seven hours on a day-long window, on the one component whose whole job is to say *when* something
happened. The 7-day screenshot is the clearest: a two-day history drawn in the middle of a week-wide
axis.

Found by looking, and only by looking. The bucket arithmetic was right, the counts were right, the
caption was right, `npm test` was green and `ng build` was clean: what disagreed was the *rendered* box
and the coordinate system the drawing was expressed in. **This is Phase 8's and Phase 5.5's lesson in a
third form** — not a rule and its application drifting apart, but a number and the space it is drawn in.

**Fixed**: the chart measures the element it is in (`ResizeObserver`, bound to the SVG through a
`viewChild` because there is no SVG until there is history) and uses that as its coordinate system, minus
the border it draws. Verified by the same probe and the same screenshots: `viewBox` `0 0 1480 160`, first
point at x=407, the curve spanning the card, the value ticks on its left edge, and — the check that
matters — **the hole in the line landing at 16 % of the width, which is where a Bad stretch twenty hours
into a twenty-four-hour window belongs.** Pinned by `src/Web/tests/trend-chart-size.test.mjs`, which
fails if the viewBox ever goes back to constants.

**The fix took two attempts and the first one is worth recording.** It measured once in
`afterNextRender`; empty history draws the words *Not enough history yet* instead of a chart, so there
was no SVG to measure, the callback returned, and the viewBox stayed a constant — confirmed by re-probing
the running client and finding `0 0 600 160` unchanged. The element arrives when the history does, so the
measurement is bound to the element and not to a moment. The test asserts that, and says why.

## What was judged, and holds

- **The caption reads as information.** *"85885 readings · 592 points · 3.80–9.70 bar"* — three facts on
  one line at the foot of the chart, legible at 1920, and it is the old caption plus the reading count it
  used to leave out. The open judgement §2.6 recorded — whether it reads as information or as clutter —
  is answered: it reads.
- **The envelope is a curve, not a comb.** At a 1008-second bucket the ripple draws as a thin band with
  the line through it, which is what the readings did; the four-second excursion is a single vertical
  reach at the far right, still visible after the reduction — the thing the whole min/max rule exists for.
- **A hole is a hole.** The ten minutes with no plottable value break the stroke, at the right place.
- **The window is the axis.** The 7-day screenshot shows two days of readings in the right-hand 28 % of
  the card and five days of honest emptiness to the left of them, which is what "plotted against the
  window asked for" is supposed to look like.

## What is still open, and what this did not do

- **The low value tick sits on the curve** at the bottom left of the plot, because the ticks are drawn
  *inside* the plot area at its left edge and the reading there is the lowest one. Crowded rather than
  wrong, and no test would ever say so.
- **The fetch budget is 600 points while the card is ~1480 px wide.** The picture is right and the
  resolution is stated, but the curve is built from fewer points than it has pixels. Asking for exactly
  the measured width needs the budget to be *the widest trend of a tag on the screen*, because one fetch
  serves every chart bound to one tag — recorded in `open-work.md` §2.6 rather than half-built here.
- **A trend in a screen tile was not walked.** The seeded screen has no `trend` component (it carries
  status and alarms), so only the Browse pane was looked at. The tile is the *other* direction of the
  same defect and the same measurement governs it, but *(the honest part)* it was not looked at.
- **Not on the on-premises stack, and not with a person at the machine.** The stack running on
  `localhost:8090` is still image `504c1d3`, built before this change; this walk ran a Gateway from the
  branch against its own database. Everything here is one machine, one browser, and a pair of eyes that
  belong to the session that wrote the code.
