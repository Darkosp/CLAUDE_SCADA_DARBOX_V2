# Walked by eye: alarm priority and OPC UA security — 2026-10-09

**The thing ADR-0033 and ADR-0034 were both waiting for.** Each shipped green, and each ended its
*Verified in review by* list with the same sentence — that nothing in it is believed until somebody has
looked at it running, because ADR-0028 and ADR-0031 had both shipped correct and broken. This is that
look, against a stack built from `dc60ea4` and served over Docker, schema at 23.

**The feature works and four things are wrong around it.** None of the four is in the ordering itself,
which is the part that was tested; all four are in the places a person actually reads an alarm. That
split is the whole lesson of the sitting.

## What held

| Claim | Seen |
|---|---|
| A threshold saved with no priority says so | **“Not yet rationalised — nobody has judged how urgent this is”** on the tag's detail |
| The select offers the three and an empty option that is a real answer | *Not yet rationalised · High — act now · Medium — act soon · Low — be aware* |
| A priority saves and reads back | set **High**, reloaded as `Priority High` |
| The ordering is by priority and not by time | Tank 3 Level (**Low**) raised 05:39:24, Discharge Pressure (**High**) raised 05:39:48 — and `/api/alarms` returns **High first**. The newer alarm sorts above the older one because it is more urgent, which is the entire feature |
| A migration gave nothing a priority | both demo thresholds came up unrationalised, and the Site's own seeded alarm did too |
| ADR-0030's marker still reads | `above 4.60` on the value tile, in the dark theme |

## 1. Rationalising a standing alarm does nothing until it next raises

**The sharpest finding, and it is a disagreement between two halves of one screen.**

The threshold was set to **High** while its alarm was standing. The tag's detail then read
`Priority High`. The standing list went on ordering that alarm **last**, below a `Low` one, because
`Alarm.Priority` is copied from the definition **at raise time** and the standing occurrence still
carried `null`.

Measured: the priority took effect **100 seconds later**, when the demo's value oscillated and the
alarm re-raised. The demo flaps every ninety seconds or so, which is the only reason this corrected
itself at all. **On a real alarm that stands for days, rationalising it would have no effect for
days** — and the screen would say `Priority High` throughout while the list disagreed.

**ADR-0034 §3 says priority is “a property of the definition”.** Carrying a frozen copy makes it a
property of the *occurrence*, which is the opposite. The freezing was copied from ADR-0025 §7, and
that reasoning does not transfer: a **deadband** is arithmetic the alarm is mid-way through using, so
changing it under a standing alarm would make it clear at a point it never raised against. A
**priority** is advice to a person about what to deal with first. Nothing is mid-calculation, and the
whole purpose of rationalising an alarm is to change that advice.

**Fixed**: the live list reads priority from the definition as it reads now. The **journal keeps the
raise-time value**, because a journal is a record of the past and has to agree with the screen somebody
was looking at — that half of ADR-0034 §5 stands unchanged.

## 2. `HIGH` now means two different things, in the same pill, on the same screen

The banner badge reads `HIGH` or `LOW` for **which limit was crossed** (`app.html:87`). Since ADR-0034,
`High` / `Medium` / `Low` are also the **priority** names.

Seen, exactly: **Tank 3 Level showed a red `HIGH` badge and had priority `Low`.** The screens
component says the same thing in bold — `Skopje/Pump House/Tank 3 Level **High** 36.1`.

**Neither vocabulary is wrong, and that is why this needed a walk rather than a review.** ISA-18.2
names priorities High/Medium/Low; the convention for the limit side is HI/LO and has been since long
before. Two standards, two correct words, one collision — and the product put them in the same visual
style with nothing to tell them apart.

**Not fixed by renaming.** Inventing `ABOVE` / `BELOW` would depart from the vocabulary a plant
engineer is trained on, which is the thing the owner's standing rule exists to prevent. The industry's
own answer is to **label** rather than to rename: an alarm list has a column headed *Priority*, and the
condition is shown as the condition. That is finding 3's fix, and it resolves this one.

## 3. Priority is invisible everywhere an alarm is actually read

It is configurable, stored, journalled, and it **orders the list** — and it appears nowhere a reader
looks:

| Where | Columns / content, as seen |
|---|---|
| The banner | badge (limit), tag path, value at raise, limit — **no priority** |
| Alarm summary (Browse) | Site · Tag · Condition · Raised · State · Acknowledged by — **no priority** |
| Journal | Recorded · Event · Tag · Value · Who · Note — **no priority**, though the column is in the database |
| Screens `alarms` component | tag path, limit word, value — **no priority** |

**A list ordered by an invisible property is worse than an unordered list.** The order looks arbitrary,
and the one thing a reader could do about it — notice that the top item is the urgent one — is exactly
what is withheld.

ADR-0034 §4 deferred **colour**, deliberately, because red is already doing two jobs in this product
(`standards-baseline.md` §4.7). **A word in a labelled column is not colour**, and the deferral was
never meant to cover it; §4's own sentence is *“colour or any other visual weight”*, and a column is
information rather than emphasis. Fixed as repair rather than as a new decision.

## 4. Found on the way: a raw float on a plant screen

The screens `alarms` component prints the value at raise unformatted:

> Skopje/Pump House/Discharge Pressure **High** 4.5600000000000005

It **overflows the card** — the digits run off the right edge. This is the arithmetic showing through,
which `formatMeasurement` exists to stop and does stop everywhere else: the banner three inches above
it renders the same number as `4.56 bar`, correctly, in the same page load.

**Nothing to do with ADR-0034** — it has been there since the component was written. It is here because
walking one feature is how the next one gets found, which is the third sitting in a row that has
happened.

## What this walk did not do

It did not exercise **OPC UA security against anything but the in-process simulator**, because the walk
stack has no OPC UA device configured and no real server to point one at. ADR-0033's
`standards-baseline.md` entry already records that as untested in the field, and it stays recorded.

It did not look at **a long alarm list**, which is where ordering earns its keep — two alarms show that
the sort works and say nothing about whether it helps during a flood.

And it did not judge whether **“Not yet rationalised”** is noticeable. It is rendered in the same muted
grey as the threshold line above it, which is deliberate under ADR-0034 §4 and may well be too quiet:
it is the only signal that an alarm has never been assessed, and it currently has the weight of a
footnote. Left as an open question rather than changed, because making it louder is a claim about
priority's visual weight, and that is ADR territory.

## What was fixed, and seen fixed

Each fix was deployed from its own commit and looked at again. Nothing below is reported on the
strength of a test alone.

| | Seen after |
|---|---|
| **1. Rationalising a standing alarm** | Tank 3 Level, standing since **07:39:24 and never re-raised**, was set from `Low` to `High` and the summary showed `High` **on the next render** — same alarm, same raise time, no retire-and-re-raise |
| | …and it **survived a Gateway restart**: the redeploy rebuilt the live list from the journal and the resolved priority came back, which is the case ADR-0034 §5 was written for |
| **2. `HIGH` meaning two things** | the banner now reads `HIGH` *(badge: the limit)* then **`priority Low`** *(labelled)* — a reader can tell them apart without knowing the product |
| **3. Priority invisible** | a **Priority** column leads the Alarm summary, so the sort order has a visible cause; the screens component carries `priority High` |
| **4. The raw float** | `above 4.55 bar`, formatted, inside its card |

**A fix that found a second defect, and then a third.** Labelling the priority on the screens component
made its line too long: it first **wrapped between a reading and its unit** — `4.54` on one line and
`bar` on the next, which is two facts where there was one — and when each piece was made unbreakable it
**clipped mid-number** at the card's edge instead, which is worse. The line now puts the tag path on its
own row with the reading, the limit and the priority beneath it. Three looks to get one list right, and
none of the three would have come from reading the code.

**The Journal deliberately still has no Priority column.** It stores one, and showing it would put the
**raise-time** priority beside a live list showing the **current** one — two different answers to one
question, three inches apart, with nothing to explain the difference. Which of the two a journal reader
wants is a decision rather than a column, and it is left open here rather than guessed.

## Still open after this sitting

- **Whether “Not yet rationalised” is loud enough.** Unchanged, and still in muted grey: it is the only
  signal that an alarm has never been assessed, and it has the weight of a footnote. Making it louder is
  a claim about priority's visual weight, which ADR-0034 §4 deferred to its own ADR.
- **A long alarm list.** Two alarms prove the sort works and say nothing about a flood.
- **OPC UA security against a real server.** The walk stack has no OPC UA device and nothing real to
  point one at; `standards-baseline.md` §2.1 keeps recording that as untested in the field.
